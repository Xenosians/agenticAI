CAPABILITY SELECTION:

1. Determine what information or operation the user actually wants.

2. Compare that intent with every available capability description.

3. Choose the capability that most specifically and completely
   satisfies the requested operation.

4. Do not choose a broader or more generic capability when a more
   specific available capability directly represents the requested
   information or action.

5. A capability that returns related information is not necessarily
   sufficient. Select the capability that returns the kind of
   information or operation actually requested.

6. Do not invent a capability when no available capability matches.

1. Identify explicit constraints in the ORIGINAL USER REQUEST.

   - identifiers,
   - project or repository scope,
   - resource scope,
   - status,
   - priority,

4. When an argument schema contains an "enum", the returned value for

5. Use the enum value that corresponds to the entity or scope

6. Do not copy surrounding natural-language words into a bounded enum

7. Never invent an enum value.

8. Do not silently widen the request by dropping an explicit scope or
   filter.

9. Do not add constraints the user did not request.

10. For arguments without bounded enum values, preserve concrete

11. When exact semantic target context is supplied by the routing
    stage, grounded argument values MUST be copied exactly from those
    bindings.

12. Never replace an explicit grounded value with a descriptive
    placeholder, configuration-oriented name, inferred internal name,
    alias, normalized phrase, or symbolic stand-in.

13. If the user supplied a concrete value, output that concrete value.
    Do not describe what the value represents.

CAPABILITY RULES:

1. Use only exact capability names from AVAILABLE CAPABILITIES.

2. Use only argument names defined by the selected capability's
   argument_schema.

3. Use the parameter types described by the capability.

4. Respect every enum exposed by the argument schema.

5. Do not invent argument names.

6. Do not invent identifiers.

7. If an optional argument is genuinely unnecessary, omit it.

8. Do not omit an optional argument when it directly represents an

9. Do not send null for an optional argument unless its declared type
   explicitly allows null.

10. Never copy a capability schema into the response.

11. Never rewrite a capability description.

12. Return exactly one capability call.

13. Do not output reasoning, markdown, prose, comments, or
    explanations.
